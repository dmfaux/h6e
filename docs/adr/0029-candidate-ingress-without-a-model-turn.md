# 0029. Candidate ingress without a model turn

- **Status:** Proposed
- **Date:** 2026-10-28 (amended 2026-10-29 after the prototype: deployment handoff, retention, opaque key)
- **Deciders:** Project lead, engineering, legal

## Context

Task 1.2 built the per-candidate workflow on eve's durable session and `defineState`, keyed on the verified WhatsApp number (ADR 0002, ADR 0003). Task 1.3 has to hand a verified application from the `/intake` webhook into that workflow, deduplicate it on the provider message id, and send one role-naming acknowledgement. Phase 1 makes no model call, and a candidate's delivery must never reach a model in this phase (ADR 0006, ADR 0014).

On eve 0.85 the only way to put a message into a durable session is a channel send (`from(address).send(...)`), and a send starts a model turn. The first Task 1.3 implementation did exactly that: a review proved by booting the build that each verified application produced an `invoke_agent` turn and a `chat anthropic/claude-sonnet-4.6` provider call carrying the candidate's number, and that nothing in the turn ran `ingest` at all.

Every other eve mechanism was checked against the eve 0.85 documentation and type declarations and by experiment, looking for a path that runs authored code inside the session (so `defineState` is available) without a model call:

- `invokeTool` runs a tool outside any conversation with no model, but "authored state starts from its initial value and is not kept" (`docs/channels/custom.mdx`).
- Dynamic schedule `run` and cross-channel `receive` either start sessions (a turn) or run outside one (no state).
- A channel `events` handler and a global hook both run inside the session with `defineState` available. A hook can cancel the turn before its model call (`ctx.cancel`). Booting the build with this shape showed the turn envelope (`invoke_agent`, outcome `cancelled`), no `chat` span, and the handler's `ingest` running, but eve discards the authored state written in a step whose turn is cancelled: the next delivery for the same number read `key: "", processedEvents: []` and sent a second acknowledgement. Cancelling at `delivery.consumed`, `turn.started` or `model.requested` gave the same result, because they are all in the step eve throws away. The eve documentation does not describe this behaviour either way, so building on it would be building on an accident.
- `eve/patterns/durable-cross-channel-notifications` states the framework position: "eve does not currently provide a direct cross-channel message queue or provider outbox. To post a notification without a model call, use the destination platform's API instead."

So an eve session cannot be driven durably without a model turn in this version. Phase 1's "no model call" boundary and Task 1.2's "state lives in `defineState`" cannot both hold for candidate ingress. One has to move, and that is an architectural decision rather than a fix.

A prototype of the Workflow SDK path (findings below) passed. It also surfaced three facts that the first draft of this ADR did not account for:

- A Workflow SDK run executes every step on the deployment that created it, for its whole life. eve hands its own idle sessions to newer deployments (`docs/concepts/execution-model-and-durability.mdx`, "When a Vercel production deployment changes"), but a run we start ourselves gets no such handoff. A per-candidate run that waits for weeks would keep running old code after every fix. It would be stranded if its deployment were removed, and this project's production deployments expire after 30 days (`deploymentExpiration.expirationDaysProduction: 30`, read from the Vercel project on 2026-10-29).
- eve applies `experimental_retention: 0` only to the runs it starts for its sessions. A run we start ourselves gets the World's plan-based default, so its completed state, including the candidate's number, stays readable after the run ends. The prototype read completed state back nine hours later.
- The hook token is Task 1.2's workflow key, `candidate:+27...`. It appears in hook records, run metadata and trace spans (`workflow.hook.token`), so the candidate's number sits in places that outlive the run's payload.

The last two are POPIA questions as much as engineering ones. How long candidate state is kept, and where the number appears, are data minimisation decisions under ADR 0006.

## Decision

Proposed, for a human to accept or replace.

The Phase 1 candidate workflow (correlation, dedup, once-only acknowledgement, and the logistics state Tasks 1.4 to 1.7 add) runs as a durable Workflow SDK function started from the verified `/intake` route, not as an eve session turn. The Workflow SDK is the durable-execution layer of the stack we already stand on (ADR 0002), and eve itself runs on it. eve resolves the `workflow` and `workflow/api` specifiers to its vendored copy for authored code, so this adds no vendor and no new dependency. There is one live run per candidate at a time, holding the same minimal state shape (ADR 0006, ADR 0012). The eve session for a candidate is reserved for Phase 2, when candidate turns do reach a model through the redacting broker (ADR 0014). It is not created in Phase 1.

**Opaque key.** The run's hook token is `candidate:` followed by an HMAC-SHA-256 of the verified E.164 number under a per-environment secret (`CANDIDATE_KEY_SECRET`). The same opaque key is the workflow key everywhere outside the run's own state. The number itself lives only in the run's state, because the acknowledgement send needs it. Hook records, run metadata, spans, logs and audit records carry the opaque key, never the number. WhatsApp message ids (`wamid.…`) are widely reported to encode the sender's number in base64, which ADR 0027's E.164 rewriter would not catch, so message ids are treated the same way: `processedEvents`, audit records and logs hold an HMAC of the message id under the same secret, never the raw id. The opaque key is pseudonymised personal information under POPIA, not anonymous data, and is handled as such.

**Ingress.** The route verifies the signature (ADR 0010) and parses the delivery. For each application it resumes the candidate's hook with the delivery, or starts a new run when no hook holds the key. "No hook, so start" is a check followed by an action, so two first messages from one number can both start a run. A first run therefore never takes the token by force. It registers its hook and awaits `getConflict()` before any step runs. If another run already holds the token, it forwards its delivery to that run with `resumeHook` and completes without doing anything else. It answers Meta 200 only after every application in the batch has been durably accepted by a run (`resumeHook` or `start` resolved), and 5xx otherwise. Meta then redelivers anything not yet accepted, and the message-id dedup keeps a redelivery to one effect. The route does not wait for the acknowledgement to be sent. The send is a step with the Workflow SDK's step retries. The event is committed to `processedEvents` only after its effects succeed, as Task 1.2's `ingestWith` already does, so a send that exhausts its retries leaves the event uncommitted and the next delivery retries it.

**Deployment handoff.** A run moves itself to the current deployment rather than staying pinned to the one that created it.

The protocol copies the shape of eve's own session handoff (`docs/concepts/execution-model-and-durability.mdx`): the target can refuse, and the new owner does nothing until the previous owner has handed over.

- **Triggers.** Every delivery the route passes to a run carries the id of the deployment that accepted it. A delivery accepted by a different deployment triggers a handoff to that deployment. The run's timer also triggers one when the run has been on its deployment for 7 days, counted from when the run started, not reset by deliveries. The timer's target is the deployment currently serving the environment's own domain, resolved in a step. It is not `deploymentId: "latest"`, which names the newest deployment and would undo an Instant Rollback.
- **One handoff at a time, nothing processed during it.** While a handoff is in flight the old run processes no delivery. It holds every delivery it receives, including the one that triggered the handoff.
- **Start.** The old run starts the successor on the target with `start(candidateRun, [state], { deploymentId, specVersion })`, passing the state only. `specVersion` is set explicitly to at least the version that supports hook takeover, because a cross-deployment start whose capability probe misses is stamped at a lower version, and a successor stamped there could never itself be taken over.
- **Claim or refuse.** The successor validates the state against a versioned schema. If it cannot read it (for example after a rollback to code older than the state), it sends `handoff.rejected` to the token, which still reaches the old run, and completes. Otherwise it claims the token with `createHook({ token, experimental_force: true })`, awaits `getConflict()` to commit the claim, and then processes nothing until the old run commits.
- **Commit.** The claim wakes the old run with `HookForceClaimedError` (checked with `HookForceClaimedError.is()`, since `instanceof` is unreliable across the workflow sandbox). The old run sends one `handoff.commit` message to the token, now owned by the successor, carrying every delivery it held in arrival order, and completes. The successor processes those deliveries first, then anything it received itself, with message-id dedup absorbing any overlap.
- **Failure.** The old run waits for the claim, a refusal, or a 10-minute deadline. On a refusal it keeps the token. On the deadline it cancels the successor run (`run.cancel()`) before taking anything back; if the claim lands first, it follows the commit path instead. In both cases it processes its held deliveries itself, writes a `candidate.handoff.failed` audit record with the opaque key and the reason, and tries again on the next trigger.
- **Never end holding the token by accident.** A run's body has a top-level catch. A run ends only through journey end, idle expiry (ADR 0030), a completed handoff, or a refused or cancelled successor. A run that ended any other way would release the token, and the next delivery would start an empty run, losing the candidate's dedup history and logistics state and sending a second acknowledgement.
- **Timers.** The run waits on its hook raced against a single `sleep` until the earliest of three times: the next handoff, the idle expiry of ADR 0030, and the next pending logistics deadline (for example a chase). All three are absolute times in the state, so a successor re-arms them exactly. Each handoff starts a fresh event log, so a run's history does not grow for the whole journey.

**Retention.** Every candidate run is started with `experimental_retention: 0`, matching the policy ADR 0027 already applies to eve's own session runs. A completed run's payload, including the number, is deleted when the run ends. Without this, each handoff would leave a completed predecessor holding a full copy of the candidate's state for the plan's retention period. The purge races any read of a completed run, so state never leaves a run by reading `returnValue`. It leaves only in three ways. The successor receives it as start arguments (handoff). A step writes it somewhere we control: the audit trail of Task 1.11, or the ATS within ADR 0012's write boundary. In Phase 2, the run pushes it to the session that takes over.

**Phase 2 pickup.** When Phase 2 introduces the eve session for a candidate, the session asks the run for a handover, the run pushes its state to the session, and the run completes. The state must reach the session's `defineState` through a step, never through a tool result, because a tool result goes to the model (ADR 0006, ADR 0014). eve's documentation only shows hooks inside workflow-tool runs, not a hook a session itself holds, so the exact mechanism is unproven. It is designed and proven in Phase 2. Phase 1 only keeps the state shape and hook protocol able to support it.

Until this ADR is accepted, `/intake` fails closed. It verifies and parses, answers Meta 200 so a verified event is not redelivered as a storm, and processes nothing. No run or session is created, no acknowledgement is sent, and no model is called. Task 1.3 is partial.

## Consequences

Task 1.2's durable binding (`candidateLogistics`, `ingest`, `inspect`, `advance`, `terminate` over `defineState`) moves to the run's state. The pure reducer, effect runner and their tests carry over. Two things in Task 1.2 change. The state gains the number and a schema version, because the key no longer carries the number (`numberFromWorkflowKey` goes). `workflowKey` becomes the keyed HMAC. Task 1.2's status line must be revisited when this lands, because "built on eve session plus `defineState`, no new ADR needed" no longer describes the system. The engineer inspect-and-advance surface (requirement E4) is rebuilt over hooks rather than session tools. Inspect becomes a hook request that the run answers by pushing its state to the caller, since `returnValue` is not readable at retention 0.

Hook records, run metadata, spans and logs hold a pseudonymised key and pseudonymised message ids instead of the number. The cost is a new secret per environment. Rotating it changes every candidate's key, so rotation needs a rekeying handoff (each run claims its new token and releases the old one) and is not a routine operation.

Code fixes reach an active candidate at their next delivery and an idle candidate within 7 days. The handoff is the most intricate part of the Phase 1 workflow, and it needs its own proof before Task 1.3 is marked done. Start a run on one preview deployment, create a second deployment, and send a delivery. Show that it executes on the second deployment (by the deployment id in the runtime log, as the prototype did), with the state intact and one acknowledgement. Prove the 7-day timer the same way, with the interval shortened in a test build. Prove the refusal, the deadline and cancel, two concurrent first messages for one number, and two concurrent deliveries during a handoff, each ending with one owner, intact state and one acknowledgement. This proof is preview-only. Under `pnpm start` there is one deployment and `deploymentId` targets do nothing, and under `eve dev` each reload is a new generation, so a reload looks like a new deployment and hooks owned by a dormant generation throw `DevelopmentRunUnavailableError` rather than `HookNotFoundError`. The route must handle that error explicitly in development.

Stuck handoffs are monitored. Repeated `candidate.handoff.failed` records for one key, and any run older than 14 days on one deployment, raise an alert. Without that, a run whose handoffs keep failing would sit until its deployment expired, and from then on `resumeHook` would fail and the route would answer Meta 5xx indefinitely. Production deployment expiry must stay comfortably above the 7-day interval. That setting becomes load-bearing, so it is recorded in the deploy notes, and nobody shortens it below 14 days without revisiting this ADR.

The Workflow SDK marks two options this design relies on as experimental: `experimental_force` on `createHook` and `experimental_retention` on `start`. The vendored Workflow packages are themselves the public `5.0.0-beta` line (eve's `docs/concepts/execution-model-and-durability.mdx`), which ADR 0005 permits; none of this is private beta. eve 0.85 uses hook takeover for its own session handoff, which it skips on a World without the `hookForceClaim` capability, and it sets retention 0 on its session runs from the trace policy. Both options are vendored inside eve, so their behaviour is pinned with eve's version, and every eve upgrade must re-run the handoff and retention proofs. If either were withdrawn, eve's own session handoff would lose the same capability, and this ADR would be revisited alongside that eve change.

Once a run completes at retention 0, its state is gone from the Workflow World. A candidate's history is reconstructed from the audit trail (Task 1.11) and the ATS, never from the run. Metadata (run ids, the opaque key, timestamps) still persists for the plan's default period, which is why the key must not carry the number. This also closes the gap ADR 0027 records, where the hook token stamped on workflow hook spans carried the workflow key and so the number.

ADR 0030 covers how long a run lives when the candidate goes quiet, and what happens when it ends.

## Alternatives considered

A hook-cancelled model turn (the experiment above). Rejected: eve discards the authored state the turn wrote, and the behaviour is undocumented.

Letting the turn run against the model with the number redacted. Rejected: Phase 1 makes no model call, the gateway has no credentials in this phase, and the turn would still cost a provider call per webhook.

A separate durable key-value store (Redis or Postgres from the Vercel Marketplace) written by the route handler, with the eve session untouched. It is viable and has no deployment pinning. But it adds a store holding candidate correlation data that ADR 0006 has to clear, needs its own retention and deletion design, and duplicates what the Workflow SDK already provides inside the stack. It was the fallback if the Workflow SDK path failed its prototype. The prototype passed, so it is not adopted.

Leaving runs pinned and keeping old deployments alive by raising deployment expiry above the longest journey. Rejected: fixes would never reach a candidate already in flight, a journey that outlasts the expiry is stranded, and deployment retention would become a silent dependency of candidate data.

Handing over from the route: on each delivery, the route ends the old run, reads its final state with `getRun(runId).returnValue`, and starts a fresh run. Rejected: it needs completed runs to stay readable (against retention 0 and ADR 0006), it does nothing for idle runs, and two concurrent deliveries for one candidate would race to start two successors.

Handing over by disposing the old hook and then starting the successor, without `experimental_force`. Rejected: between the dispose and the successor's `createHook`, a delivery finds no hook. The route then starts a new run with empty state, and the candidate's dedup history and logistics state are lost.

The number as the hook token, as in the first draft and the prototype. Rejected: hook records, run metadata and spans outlive the payload, so the number would persist past any payload retention we set.

Keeping the first implementation (send into the session, model turn per webhook). Rejected: it puts the candidate's number in front of a model (ADR 0006, ADR 0014) and never runs `ingest`, so it fails the task on both counts.

## Prototype findings

Recorded against the first draft of this ADR. The amended Decision answers the gaps these findings name: the acknowledgement failure path, the deployment pinning, the retention, and the number in the hook token. The `returnValue` handover described under Question 3 is superseded by the Decision's retention 0 and push-based pickup.

Run on 2026-10-28 and 2026-10-29 against the prototype on branch `prototype/adr-0029-workflow-ingress` (commits 332b8b7, 07f23a5, a1a57d6, 53af53e). Method: Meta-shaped payloads signed with the configured app secret, posted to `/intake`, locally (`pnpm build`, then `tail -f /dev/null | PORT=3920 pnpm start`, with a Graph stub on port 3918) and on Vercel preview deployments of the branch (with `WHATSAPP_GRAPH_BASE_URL` pointed at the deployment's own `/prototype/fake-graph` route). Secret-gated prototype routes (`/prototype/run`, `/prototype/handover`, `/prototype/run-by-id`) observed the runs from outside. Only fake numbers of the form +2782000000x were used. The branch-scoped preview secrets were removed afterwards.

### Question 1: does `start()` from `workflow/api` work from an eve channel route?

Pass, locally and on Vercel.

Local, 2026-10-29, fresh build of 53af53e: a forged signature got 403. Application A for +27820000011 answered `{"action":"started","runId":"wrun_01M62XBMAZ24VXZQ15NR9V76F1"}`. A redelivery of the same message id answered `resumed` with the same run id. Application B (same number, new message id) answered `resumed` with the same run id. Application C for +27820000012 started `wrun_01M62XBX69RKA9RPZ1ADJCKW23`. The Graph stub logged exactly one POST per number. The step log read `acknowledged=true processedEvents=1 completedEffects=1` once per run and `acknowledged=false` for every later delivery. The console span exporter printed `workflow.start candidateRun`, `workflow.run workflow//./src/workflow/candidate-run//candidateRun`, `step.execute handleDelivery`, `step.execute initialState`, `world.hooks.getByToken`, `hook.resume` and the usual `world.*` spans, and zero `invoke_agent` or `chat` spans. The same sequence passed on 2026-10-28 against the 332b8b7 build (runs `wrun_01M60ZY1Q5T1AW0NM3TFPBHXW0` and `wrun_01M60ZYAM4BZCXQ1FVH7CNNZXH`, two stub posts for two numbers).

Vercel preview, 2026-10-28, deployment `h6e-4s7cl76yz`: forged 403; +27820000003 started `wrun_41M616X2P50GR82JP3G77C0FBW`, its redelivery and its second message both `resumed` that run, +27820000004 started `wrun_41M616XGAP0GN21E99FKC7RHWM`. Runtime logs show one `[fake-graph] POST` per number and `acknowledged=true` once per run. `vercel logs --environment preview --since 24h -q invoke_agent` and `-q "chat anthropic"` returned no records.

One gap in the prototype against this ADR's Consequences: the route awaits `start()` or `resumeHook()` and answers Meta 200 before the acknowledgement step has run, so the "answer Meta 5xx on a failed send" story is not implemented. The run design supports it (the ack is a step whose outcome the route could wait on), but it was not proven.

### Question 2: trace policy retention, and state across deliveries and redeploys

Pass on both parts, with one consequence that must be designed for before acceptance.

Retention. eve 0.85 passes `experimental_retention: 0` to the Workflow SDK only for the runs it starts for its own sessions (`startSession` in `execution/workflow-runtime.js` derives it from the resolved trace policy). An authored `start()` from `workflow/api` passes no retention option, so the World's default retention applies, not ADR 0027's policy. Confirmed empirically: runs `wrun_41M619GT690GWXNQ8GV7H7A2QG` (completed 2026-10-28T18:44:19Z) and `wrun_41M61CYCFR0GKCGV2QSNTPMFAD` (completed 2026-10-28T19:13:12Z) were read by id on 2026-10-29T04:09Z from a later deployment and returned `status: "completed"` with the full return value (the candidate state with `processedEvents` and `completedEffects`). So completed payloads are not deleted under the current policy. The flip side is that per-candidate state is retained for the plan's default period after the run ends, which ADR 0006 has to weigh. The Workflow SDK documents that at `experimental_retention: 0` the purge usually wins the race against `returnValue`, so if retention 0 is chosen the final state must leave the run through a step we control, not be read back.

Across deliveries. A run parked on its hook accepted three and four deliveries spread over fifteen hours and kept its state (for example +27820000008 ended with `processedEvents: ["wamid.xdeploy3.B","wamid.r2x1.B","wamid.r2x2.B"]`, `completedEffects: ["ack:started:candidate:+27820000008"]`). Locally the run also survived a server restart: the restarted server resumed `wrun_01M62XBX69RKA9RPZ1ADJCKW23` and its handover state held both deliveries.

Across redeploys. Run `wrun_41M61YWT460GV41KED3QXPY7KE` was started on deployment `h6e-nxu0id6w3` (`dpl_BbTHpWKo2xHXK9YZjGsYmBLeywC2`) on 2026-10-28T19:13Z. Two further deployments of the branch followed (`h6e-rdcz3snfz`, `dpl_Hc2RdrQ2bVPjznBYrczmwXsu4kmH`, 04:05Z, and `h6e-hv8fneopj`, `dpl_3XvMfnL74FS4ikDwBUjw2Lpn4gfL`, 04:10Z on 2026-10-29). A delivery through the branch alias after each one was accepted by the new deployment and answered `resumed` with the same run id, `/prototype/run` still reported `running`, and the final handover state carried all three deliveries. The same held the day before for +27820000007 across `h6e-4s7cl76yz` to `h6e-nxu0id6w3` (`processedEvents: ["wamid.vprev3.A","wamid.vprev3.B","wamid.xdeploy1.B"]`).

The consequence. In every cross-deployment case the step executed on the deployment that created the run. The runtime log for `POST /intake` carries the new deployment id and, about half a second later, the `[candidate-run] delivery handled` line under `POST /.well-known/workflow/v1/flow` carries `dpl_BbTHpWKo2xHXK9YZjGsYmBLeywC2`, in the old deployment's log format. A Workflow run is pinned to its creating deployment for its whole life. eve's own sessions have a deployment handoff; a bare run does not. For a per-candidate run that waits for weeks this means the deployment that received a candidate's first message must stay available until that candidate's run ends, code fixes do not reach existing runs, and Vercel's deployment retention settings become load-bearing. Before acceptance, the design needs a handoff of its own, for example the route noticing the owner deployment differs from the current one, handing the run over, and starting a fresh run on the current deployment seeded with the returned state. The primitives for that are proven here; the prototype's run body does not yet accept an initial state.

### Question 3: how a Phase 2 eve session picks up Phase 1 state

Answered in writing; the primitives are proven, the session-side call was not run.

The hook token is Task 1.2's workflow key (`candidate:+27...`), so any host code that knows the verified number can find the run with `getHookByToken(key)`, end it with `resumeHook(key, { kind: "handover" })`, and read its final state with `getRun(runId).returnValue`. The prototype's `/prototype/handover` route did exactly this locally and on preview and received the full state each time (for example the 007 and 008 states quoted above). eve's documentation (`docs/tools/workflows.mdx`) places `start`, `getRun` and `resumeHook` from `workflow/api` inside `"use step"` functions of a `defineWorkflowTool`, so the Phase 2 session keyed on the same number can run that handover in a step on its first turn and seed its `defineState` slot from the returned state. What was not run is an actual eve session doing this, because Phase 1 has no model credentials and a session turn would be a model call; it should be the first Phase 2 spike. If retention is set to 0 for these runs, the handover must push the state to the session rather than have the session read `returnValue` (see Question 2).

### Not safe to ship from the prototype

The three `/prototype/*` read and handover routes authenticate with the webhook app secret sent as a request header, which reuses a signing secret as a bearer and exposes per-candidate state and run ids. `/prototype/fake-graph/...` is an unauthenticated POST that logs request bodies. `WHATSAPP_GRAPH_BASE_URL` lets an environment misconfiguration redirect candidate messages, which carry the number, to an arbitrary host. The route answers Meta before the acknowledgement step has run. All of these are for the prototype only and must not survive into the Task 1.3 implementation.
